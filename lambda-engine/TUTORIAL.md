# REPL за 15 минут

REPL — это интерактивный интерпретатор: он читает введённую строку, вычисляет её и печатает результат, и так по кругу (read, eval, print, loop). Это прогулка по REPL λ-термов с файлом [tutorial.lam](tutorial.lam) под рукой. В нём определения с лекции и четыре маленькие задачи: две решены, одна с дыркой, одна наполовину. Файл можно и нужно править и ломать: домашки устроены точно так же, только задач больше.

Запуск из корня репозитория домашки:

```
make repl FILE=lambda-engine/tutorial.lam
```

REPL напечатает `Loaded lambda-engine/tutorial.lam` и приглашение `>`, после которого вводятся термы и команды. Выход: `:q` или Ctrl-D. Дальше каждая команда сначала показана, потом её вывод.

Без `FILE` открывается `src/hw.lam`.

## 1. Синтаксис: дерево терма

Терм — это дерево, а строка с точками и скобками лишь его запись. Когда непонятно, к чему относится переменная или где проходят границы аппликации, попросите нарисовать терм:

```
> :explain \x. x (a x)
\x. x (a x)

free  a

\ x
`-- @
    |-- x
    `-- @
        |-- a
        `-- x
```

`@` — узел аппликации, `\ x` — абстракция, ниже — её тело. Свободные переменные перечислены отдельно. В файлах домашек они называются буквами из начала алфавита (`a`, `b`, `c`), а связанные — из конца (`x`, `y`, `z`), так по букве видно, что есть что; допустимые свободные переменные перечислены в строке `vars` в начале файла. Имена из файла помечены как `(env)`:

```
> :explain S K K
S K K

free  S (env), K (env)

@
|-- @
|   |-- S
|   `-- K
`-- K
```

## 2. β-редукция

Если ввести терм без команды, он редуцируется до нормальной формы и печатается:

```
> K a (I b)
a
```

Интереснее путь к ответу. `:step` делает один шаг, `:follow` показывает все:

```
> :follow K a (I b)
K a (I b)
^
~K~> (\x y. x) a (I b)
     ^~~~~~~~~~~
~b~> (\y. a) (I b)
     ^~~~~~~~~~~~~
~b~> a
```

Каретка `^~~~` под термом отмечает редекс, который сработает следующим. Стрелка перед следующей строкой говорит, что произошло: `~K~>` — раскрыто определение `K`, как ⇝<sub>K</sub> на практике; `~b~>` — β-шаг. В терминале редексы ещё и подсвечены цветом. Заметьте, что `I b` так и не был вычислен: по умолчанию REPL идёт в нормальном порядке и отбрасывает аргумент раньше, чем доберётся до него.

Именно такие цепочки шагов проверяются в домашках командой `chain`: строка на шаг, стрелка перед каждой. Посмотрите на задачу 1.2 в файле, это трасса `S K K` до `I`, записанная руками.

## 3. Правим файл, не выходя из REPL

Так выглядит работа над любой задачей. В задаче 1.3 у `compose` стоит дырка, и пока она там, терм с ней вычислить нельзя:

```
> compose suc suc 0
error: hole in ‘compose’
```

Откройте `tutorial.lam` в редакторе и замените строку на `compose := \f g x. f (g x)`. Затем в REPL:

```
> :r
Loaded lambda-engine/tutorial.lam
> compose suc suc 0
\s z. s (s z)
```

`:r` перечитывает файл целиком; определения, сделанные в REPL, при этом пропадают. Если в файле после правки ошибка разбора, `:r` печатает её с номером строки и оставляет старые определения, работать можно дальше. Ответ `\s z. s (s z)` — это число Чёрча ⌜2⌝; как читать такие ответы, рассказано в разделе 5.

## 4. Определения и α-эквивалентность

Определение в REPL выглядит так же, как в файле: имя, `:=`, терм. Числа сразу разворачиваются, поэтому эхо длиннее ввода:

```
> three := plus 1 2
three := plus (\s z. s z) (\s z. s (s z))
```

Определение хранится как написано, а не в нормальной форме, поэтому `:follow three` покажет и раскрытие `plus`. Все имена сессии перечисляет `:env`: сначала из файла, в конце `three`. Определение через `=` вместо `:=` не проходит:

```
> K = \x y. x
error: a definition is written with ‘:=’: K := …
```

Незнакомое имя в REPL просто остаётся свободной переменной, `foo a` напечатает `foo a`. Проверялка строже: в файле любое имя, которого нет ни в определениях, ни в строке `vars`, считается опечаткой.

Два терма, отличающиеся только именами связанных переменных, — один и тот же терм. Это проверяет `:eq-a`, без всякой редукции и без раскрытия имён:

```
> :eq-a (\x y. x) (\y z. y)
True
> :eq-a (\x. x a) (\y. y y)
False
> :eq-a K (\y z. y)
False
```

Последний ответ `False` потому, что `K` здесь — имя, а не его определение. Составные термы берите в скобки, иначе они склеятся в одну аппликацию.

## 5. Кодирование данных

Пары, логические значения и числа в λ-исчислении — это функции, и нормальная форма показывает их как функции:

```
> plus 2 3
\s z. s (s (s (s (s z))))
```

Числа в файле и в REPL — это числа Чёрча, поэтому ответ выглядит так. Чтобы прочитать результат как число, пару, список или булево значение, есть `:decode`:

```
> :decode plus 2 3
⌜5⌝
> :decode pair 1 (pair true false)
⟨⌜1⌝, ⟨true, ⌜0⌝⟩⟩
```

Во второй строке `false` напечатано как ⌜0⌝: у `\t e. e` и у ⌜0⌝ одна и та же нормальная форма, декодер не может их различить, и это правильно. Обратное тоже бывает: декодер узнаёт только термы, записанные ровно как ⌜n⌝, поэтому `\z. z` он оставит как есть, хотя от ⌜1⌝ = `\s z. s z` этот терм отличается лишь η-раскрытием. Проверка `expect` сравнивает с точностью до η и такой ответ примет за ⌜1⌝. Проверялка тоже печатает результаты через декодер, так что сообщения вроде «получено ⌜7⌝, ожидалось ⌜8⌝» читаются сразу.

## 6. Стратегии редукции и зацикливание

В разделе 2 REPL шёл в нормальном порядке: самый левый внешний редекс, аргументы не вычисляются, пока не понадобятся. На практике это называлось ленивой стратегией, и REPL принимает оба имени, `normal` и `lazy`. Энергичная стратегия, где аргумент вычисляется до подстановки, называется `strict`; её можно вписать перед термом:

```
> :follow strict K a (I b)
K a (I b)
^
~K~> (\x y. x) a (I b)
     ^~~~~~~~~~~
~b~> (\y. a) (I b)
              ^
~I~> (\y. a) ((\x. x) b)
             ^~~~~~~~~~~
~b~> (\y. a) b
     ^~~~~~~~~
~b~> a
```

Здесь `I b` вычисляется до подстановки, лишних два шага. Третья стратегия называется `applicative`: самый левый внутренний редекс, аргументы вычисляются в первую очередь. Список всех команд с описанием стратегий печатает `:help`.

Нормальной формы может и не быть. `omega` из файла редуцируется в самого себя, и REPL сдаётся по лимиту шагов, а не виснет:

```
> omega
error: did not reach normal form (reduction limit)
```

## 7. Типы

`:type` выводит наиболее общий простой тип по Карри:

```
> :type K
K : α -> β -> α
> :type S
S : (α -> β -> γ) -> (α -> β) -> α -> γ
> :type twice
twice : (α -> α) -> α -> α
> :type omega
error: бесконечный тип: α ∼ α -> β
```

Третья домашка использует `language typed`: там числа — литералы `Int`, а `plus`, `mult`, `if` и другие примитивы встроены; REPL узнаёт язык из загруженного файла, отдельно переключать его не нужно.

## 8. Проверка файла

Проверки в файле — это открытые тесты, и гоняет их тот же раннер, что проверяет домашку по `make check`. Ему можно передать другой файл:

```
make check FILE=lambda-engine/tutorial.lam
```

Сначала отрабатывает линтер Haskell-кода, для λ-домашки ему сказать нечего, затем идут задачи. Для исходного файла вывод такой:

```
Running test "1.1":
    Done :)
Running test "1.2":
    Done :)
Running test "1.3":
    [TODO] 1.3:0:expect compose suc suc 0 = 2 Not implemented: в ‘compose’ осталась дырка (...)
    [TODO] 1.3:1:expect compose suc (K 0) 5 = 1 Not implemented: в ‘compose’ осталась дырка (...)
    Not started yet
Running test "1.4":
    [TODO] 1.4:1:minimal given = ... Not implemented: в терме осталась дырка (...)
    [TODO] 1.4:2:rename given = ... Not implemented: в терме осталась дырка (...)
    In progress, 33% tests remain :|

1.1     level 1  DONE
1.2     level 1  DONE
1.3     level 1  TODO
1.4     level 1  PARTIAL 33%
Level 1: open (missing: 1.3 1.4)
```

Каждая проверка файла — отдельный тест, рядом с ней стоит её строка из файла и причина. Проверка, упёршаяся в дырку, помечена `[TODO]`: к задаче ещё не приступали, и задача целиком получает статус TODO, а не FAILED. Внизу таблица статусов и вердикт по уровню; пока уровень 1 открыт, `make check` завершается с ошибкой, в домашке это значит «сдавать рано».

Теперь поэкспериментируйте, каждый раз запуская проверку заново.

**Неверный ответ.** Впишите `compose := \f g x. g (f x)`, порядок перепутан:

```
Running test "1.3":
    [FAILURE] 1.3:1:expect compose suc (K 0) 5 = 1 слева получается ⌜0⌝, а справа ⌜1⌝
    In progress, 50% tests remain :|
```

Первая проверка прошла, потому что `suc` с самим собой коммутирует; вторая поймала ошибку: `K 0 (suc 5)` даёт ⌜0⌝, а нужно `suc (K 0 5)`, то есть ⌜1⌝. Задача стала PARTIAL.

**Лишние скобки.** Впишите `minimal given = \x. (x (a x))`:

```
    [FAILURE] 1.4:1:minimal given = \x. (x (a x)) остались лишние скобки: можно убрать ещё 1 пару скобок
```

Сам ответ проверялка не печатает: найти лишнюю пару и есть задача.

**Сломанная цепочка.** В задаче 1.2 замените в пятой строке `~K~>` на `~S~>`:

```
Running test "1.2":
    [FAILURE] 1.2:3:chain skk to I =, строка 5 строка 5 получается из строки 4 раскрытием ‘K’, а не ‘S’
```

А если испортить сам терм, например написать в шестой строке `\z. (\y. y) (K z)` вместо `\z. (\y. z) (K z)`, проверялка укажет обе пострадавшие строки и подскажет, какие шаги были возможны:

```
Running test "1.2":
    [FAILURE] 1.2:4:chain skk to I =, строка 6 строка 6 не получается из строки 5 одним β-шагом; возможные шаги: \z. (\y. z) (K z)
    [FAILURE] 1.2:5:chain skk to I =, строка 7 строка 7 не получается из строки 6 одним β-шагом; возможные шаги: \z. K z
```

Шаг проверяется относительно предыдущей строки, поэтому одна ошибка портит два перехода: неверный шаг к строке 6 и шаг из неверной строки 6.

**Всё решено.** Верните цепочку, впишите `compose := \f g x. f (g x)`, `minimal given = \x. x (a x)` и `rename given = \x1. x1 (a x1)`:

```
1.1     level 1  DONE
1.2     level 1  DONE
1.3     level 1  DONE
1.4     level 1  DONE
Level 1: closed
```
